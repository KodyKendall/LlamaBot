## The slash menu opens mid-sentence

`/` used to only open the menu as the first character of an empty composer, and every
pick took the whole box with it. Now a `/` at any word boundary opens it, and a pick
swaps **only** the `/…` you typed.

**Setup**

- Box: https://llamapress-dev.llamapress.ai, chat UI. Frontend change — hard refresh.
  The skill-token prompt wording also changed, so force-recreate for that half.
- Code: `app/frontend/chat/ui/SlashCommandManager.js` (`findSlashTrigger`,
  `replaceSlashToken`). Automated coverage: `app/tests/js/slash_menu_midmessage.test.mjs`.

- [ ] Type `remind me to /re` — the command menu opens, filtered to `/restart`.
- [ ] Pick a **skill** mid-sentence: `before the deploy /rails-mig` → the token becomes
      `/rails-migration ` and the words before it are untouched. Add words after it and
      send: Leo loads the skill and does the work (it no longer needs to lead the message).
- [ ] Pick a **host command** mid-sentence (`hang on, let me /restart`): the confirm
      dialog appears and your sentence stays in the box minus the `/restart` token.
- [ ] Pick a host command from an empty composer: the box ends up empty, as before.
- [ ] `/skills` and `/cookbook` picked mid-sentence swap in their own token and open
      their list, leaving the sentence alone.
- [ ] Typing a path — `look in app/frontend`, `docs/cookbook` — opens nothing.
- [ ] A bare slash mid-sentence (`what is 5 /`) opens nothing, so Enter still just sends.
      A bare `/` in an empty composer still opens the full menu.

## `/cookbook` mid-sentence (the recipe reference)

`/cookbook` used to only work as the first thing in an empty composer, and picking a
recipe replaced everything you had typed with a paragraph-long instruction. Now the
search triggers wherever the caret is — mid-thought counts — and a pick swaps **only**
the `/cookbook …` text for a short reference:

```
@cookbook:pdf-download-export (https://llamapress.ai/cookbook/pdf-download-export.json)
```

The agent prompts recognize that shape and curl the URL for the full recipe.

**Setup**

- Box: https://llamapress-dev.llamapress.ai, chat UI, any role.
- **Frontend + prompt** change. The JS needs a hard refresh (Cmd/Ctrl-Shift-R); the
  prompt edit is Python, so force-recreate before testing the agent half:
  ```bash
  cd ~/dev/Leonardo && docker compose -f docker-compose-dev.yml up -d --force-recreate llamabot
  ```
- Code: `app/frontend/chat/ui/SlashCommandManager.js`, the `COOKBOOK` section of each
  agent's `prompts.py`. Automated coverage: `app/tests/js/cookbook_slash_command.test.mjs`,
  `app/tests/test_cookbook_mention_prompt.py`.

**The menu**

- [ ] In an empty composer, `/cookbook` opens the recipe list; typing `pdf` after it
      filters to PDF recipes.
- [ ] Type a sentence first — `add a pdf export to the invoices page ` — then `/cookbook`
      **at the end of it**. The recipe list opens without the sentence being touched.
- [ ] Keep typing `pdf` after the mid-sentence `/cookbook`: the list filters the same way
      it does from an empty composer.
- [ ] Escape closes the list and leaves every character you typed in place.

**The pick**

- [ ] Click a recipe from a mid-sentence search. Only `/cookbook pdf` is replaced — the
      words before AND after it survive, with single spaces around the reference.
- [ ] The caret sits right after the reference, so you can keep typing without clicking.
- [ ] Enter (with a row highlighted) inserts the reference instead of sending the message.
      Nothing is sent until you press Enter a second time.
- [ ] Tab on a highlighted row does the same thing as Enter.
- [ ] The ↗ icon on a row still opens the recipe on llamapress.ai and does **not** insert
      anything into the composer.

**The agent half**

- [ ] Send a message containing a picked reference plus your own words, e.g.
      `@cookbook:pdf-download-export (…json) — put the button on the invoices page`.
      Leo curls that URL early in the turn (watch the tool calls) and follows the recipe.
- [ ] It applies the recipe to *your* words — the invoices page, not a generic demo page.
- [ ] Ask a normal question with no reference in it: Leo does **not** curl the cookbook
      for no reason.

**The Enter key** (regression-sensitive — ChatApp's send lives on the same textarea)

- [ ] With the recipe list open, Enter inserts the highlighted recipe and the message
      stays in the box. Nothing is sent.
- [ ] Press Enter a second time: *now* it sends, with the reference in the message.
- [ ] Same for the normal `/` command menu — Enter runs the highlighted command (or opens
      its confirm) and never also sends what you typed.
- [ ] ↑/↓ move the highlight without sending; Escape closes the menu without sending.
- [ ] `/cookbook zzzz` (no matches) + Enter: the menu has nothing to give, so the message
      sends normally rather than the Enter key looking dead.
- [ ] Shift+Enter with the menu open inserts a newline, as it does everywhere else.
- [ ] With no menu open, Enter sends and Shift+Enter newlines — exactly as before.

**Negative cases**

- [ ] `docs/cookbook` or `app/frontend` typed in a sentence does NOT open the recipe list
      (the `/` must start a word).
- [ ] `/cookbooks` (plural) does not open the recipe list.
- [ ] With the cookbook unreachable (kill your network, then `/cookbook`), the list says
      it couldn't load rather than hanging or clearing your message. Restore the network,
      retype `/cookbook`, and the recipes come back.

## Preview JavaScript errors (Show Leo)

When the Rails app preview throws a JavaScript error, one quiet line appears above the
composer:

```
resting:   • 2 errors detected                          [x] Show Leo   ×
hovered:   • 2 errors detected  Read more               [x] Show Leo   ×
```

**Show Leo is checked by default**, which means those errors ride along with your next
message automatically — no clicking. Unchecking holds them back; the × dismisses the row
and also stops them being sent. **Read more** stays invisible until you hover the row, and
opens a popup that explains what broke in plain language, with the technical detail
underneath.

It is intentionally understated — it sits under the composer for as long as the app is
broken, so it should read as a footnote, not an alarm.

The chat page and the preview are different origins, so the browser will not let the chat
read the iframe's errors — the app **pushes** them up over postMessage instead. That is
why the origin cases below matter as much as the UI ones.

**Setup**

- Box: https://llamapress-dev.llamapress.ai, chat UI, any role.
- **Frontend-only on both sides.** Hard refresh the chat (Cmd/Ctrl-Shift-R) — that
  reloads the preview iframe too, which is what picks up the Rails half. No
  force-recreate. If the row never appears, confirm the new asset is actually served
  before debugging anything else:
  ```bash
  curl -s http://localhost:3000/ | grep -o '"llamapress/error_push_targets": "[^"]*"'
  ```
- Code: `llamapress/console_capture.js`, `llamapress/error_push_targets.js` and
  `llamapress/early_error_buffer.js` plus the inline head snippet in
  `layouts/_llamapress_page_context.html.erb` (Rails side, mirrored in Leonardo
  `rails/app` and the LlamaPress-Simple skeleton),
  `app/frontend/chat/ui/ErrorAttach.js` (chat side). Automated coverage:
  `app/tests/js/preview_js_error_attach.test.mjs` (via
  `app/tests/test_frontend_preview_js_error_attach_js.py`),
  `rails/spec/javascript/llamapress/error_push_targets.test.js`,
  `rails/spec/javascript/llamapress/early_error_buffer.test.js`.
- To fire errors on demand, open the preview in its own tab and run in its console:
  ```js
  console.error('boom', new TypeError('x is not a function'));   // console.error
  setTimeout(() => { undefinedFn(); });                          // uncaught
  Promise.reject(new Error('fetch failed'));                     // unhandled rejection
  ```

**Errors that happen while the page LOADS** (the case that matters most)

`console_capture.js` is a deferred module, so it does not exist yet while the body is
parsing. A separate inline script in the layout head buffers page-load errors and hands
them over — without it, "I opened the page and it's broken" was recorded nowhere.

- [ ] Add a deliberately broken inline script near the bottom of a page the preview
      shows, e.g. in `rails/app/views/public/welcome.html.erb`:
      ```erb
      <script>nonExistentFunctionThatWillCrash();</script>
      ```
- [ ] Reload the preview. The row appears **on load**, with no interaction, reading
      "1 error detected".
- [ ] **Read more** shows the ReferenceError with the file and line it came from.
- [ ] Remove the broken script, reload — the row is gone.

**The row**

- [ ] With no errors on the page, there is no row above the composer at all.
- [ ] Trigger a `console.error` in the preview — the row appears within a second reading
      "1 error detected", with **Show Leo** already checked.
- [ ] It is genuinely unobtrusive: one thin line of dim text, no coloured panel, no
      border. It should not pull your eye away from the composer.
- [ ] Trigger an uncaught error and an unhandled promise rejection. All three kinds are
      counted; the row still occupies exactly one line.
- [ ] Fire the **same** error 20 times. The count reads 20 — but it is still one line,
      and **Read more** shows a single entry saying it happened 20 times.
- [ ] The × dismisses the row. A repeat of an error you already saw does **not** reopen
      it; a genuinely new error does.

**The Read more affordance (hover-only)**

- [ ] At rest — mouse anywhere else — the row reads just "N errors detected" with the
      Show Leo box. **No "Read more" is visible.**
- [ ] Hover anywhere on the row and "Read more" fades in, small and dim.
- [ ] The row does **not** move, resize, or reflow when it appears — the text after it
      stays exactly where it was.
- [ ] Move the mouse away and it fades back out.
- [ ] Tab to it with the keyboard (no mouse): it becomes visible on focus, so the popup
      is reachable without hovering.

**The Read more popup**

- [ ] **Read more** opens a popup headed "Something on this page isn't working".
- [ ] Each error leads with a **plain-language sentence** a non-developer could act on
      ("The page tried to use something that doesn't exist."), with the raw error text
      in smaller mono type underneath — not the other way round.
- [ ] Check the wording matches the failure: a `ReferenceError` says something doesn't
      exist, a `TypeError` says a value was used wrongly, a failed `fetch` mentions the
      server, and an unhandled rejection mentions a background task.
- [ ] **Technical details** expands to the full stack trace; it is collapsed by default.
- [ ] The popup says Leo will see these with your next message. Now untick **Show Leo**
      and reopen it — the wording changes to tell you they are NOT being sent.
- [ ] It closes via **Got it**, the ×, clicking the dark backdrop, and the Escape key.
- [ ] Clicking **Read more** twice does not stack two popups.
- [ ] Send a message while the popup is open — it closes itself (it was describing
      errors that have now been sent and cleared).

**Sending (the point of the feature)**

- [ ] With errors showing and **Show Leo** left checked, type a question and send. Leo's
      reply shows it has the actual error — it references the real message and stack, not
      a guess.
- [ ] The row disappears after that send: those errors were consumed.
- [ ] Trigger a new error, **uncheck** Show Leo, and send. Leo does **not** receive the
      error, and the row stays (with the box still unchecked) so you can change your mind.
- [ ] Re-check the box and send again — now it goes.
- [ ] Dismiss the row with ×, then send. Nothing error-related is attached.
- [ ] Send a message with no errors present: no `<PAGE_JS_ERRORS>` block, nothing odd in
      the transcript.

**Interaction with Capture logs**

- [ ] With errors showing, use the 🐛 **Capture logs** button. It still returns JS console
      logs as before, and the error row is **not** cleared by it. (These are separate
      channels — the old one drains the iframe's buffer, this one does not touch it.)

**Origin safety**

- [ ] Navigate the preview between several pages, firing an error on each. Hovering the
      count shows each error with the path it actually came from.
- [ ] Errors from the chat page itself (run `console.error('chat side')` in the top-level
      console) do **not** appear — only the preview's errors do.
- [ ] An error whose message contains HTML, e.g.
      `console.error('<img src=x onerror="alert(1)">')`, shows as literal text in the
      Read more popup. No image, no alert, no broken layout.

## Escape hides the building screen

While Leo works in beginner, engineer or plan mode, a "Your App is Building!" overlay
covers the preview pane. It has always had a **Hide ×** pill in its corner; Escape now
does the same thing from the keyboard.

**It hides, it does not cancel.** Leo keeps working, the run finishes normally, and the
chat transcript is untouched — the same contract the Hide pill already had.

**Setup**

- Box: https://llamapress-dev.llamapress.ai, chat UI.
- **Frontend-only.** Hard refresh (Cmd/Ctrl-Shift-R) — no force-recreate.
- Code: `app/frontend/chat/ui/IframeManager.js` (`initOverlayEscapeListener`).
  Automated coverage: `app/tests/js/building_overlay_escape.test.mjs` (via
  `app/tests/test_frontend_building_overlay_escape_js.py`).

**The basic gesture**

- [ ] In **engineer** mode, send a request that takes a while. The building overlay
      appears over the preview. Press **Escape** — the overlay disappears and you can
      see and click the app preview underneath.
- [ ] Leo is still working: the chat keeps streaming, tool calls keep landing, and the
      turn completes normally with the app actually changed.
- [ ] Repeat in **beginner** mode and in **plan** mode (execution mode → Plan). Same
      behaviour in all three.
- [ ] The **Hide ×** pill still works exactly as before.

**When Escape should do nothing**

- [ ] With no build running (no overlay on screen), pressing Escape in the chat does
      nothing surprising — no layout shift, no console error.
- [ ] Press Escape a second time after the overlay is already hidden. Nothing happens.
- [ ] Open the `/cookbook` menu **while no build is running** and press Escape: the menu
      closes as it always did.

**Focus and interaction**

- [ ] Start a build, click into the composer and start typing, then press Escape without
      clicking away. The overlay hides (this is the main case — you should not have to
      click out of the input first).
- [ ] Your typed text is still in the composer afterwards, unsent.
- [ ] Start a build, hide the overlay with Escape, then send a **second** message. The
      overlay comes back for the new run — hiding it once does not disable it forever.

**Edge**

- [ ] Trigger a question from Leo that renders inside the overlay ("Question from Leo"),
      then press Escape. The overlay hides and the same question card is still there in
      the chat, still answerable. Answering it continues the run.

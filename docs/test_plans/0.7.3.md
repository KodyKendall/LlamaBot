## Discard no longer destroys work permanently

**Discard** in the History panel ran `git checkout -- .` + `git clean -fd` with no
snapshot of any kind. A paying customer clicked it and lost their entire app — a young
Leo app is almost all *untracked* files, so `clean -fd` deleted the whole thing and there
was nothing left to recover from.

Now a `git stash push --include-untracked` snapshot is taken **first**, pinned under its
own `refs/llamabot/discards/*` ref (so `git stash clear`, `git stash pop` or gc can't
take it away), and an **Undo discard** button restores it. If the snapshot can't be
written, the discard does not happen at all.

**Setup**

- Change is in **LlamaBot** — needs a released image or a `--force-recreate` (uvicorn
  runs without `--reload`), plus a hard refresh for the panel JS/CSS.
- Code: `app/services/checkpoint_service.py`, `app/routers/checkpoints.py`,
  `app/frontend/chat/checkpoints/CheckpointManager.js`, `app/frontend/style.css`.
  Automated coverage: `app/tests/test_checkpoint_discard_backup.py`.
- Git commands below run in the llamabot container against the Leonardo repo:
  `docker exec leonardo-llamabot-1 git -C /app/leonardo <cmd>`.

**The round trip — this is the one that matters**

- [ ] With Leo, edit an existing page **and** create a brand-new one (so there is both a
      modified tracked file and an untracked file). Don't save a checkpoint.
- [ ] Open the History panel. The amber "Unsaved changes" banner shows both files.
- [ ] Click **Discard**. The confirm dialog says a backup is saved and this can be undone
      — it must NOT say "cannot be undone".
- [ ] Confirm. The app reverts, and the toast reads `Discarded N file(s) — click "Undo
      discard" to get them back.`
- [ ] A green **Undo discard** banner appears, naming the number of restorable files.
- [ ] Click **Undo discard**. Both the edit and the brand-new page come back, and the
      preview iframe reloads showing them.
- [ ] The "Unsaved changes" banner is back with the same file list.

**The snapshot is real and durable**

- [ ] After a discard: `git -C /app/leonardo for-each-ref refs/llamabot/discards` lists a
      ref, and `git show <sha>^3 --stat` shows the untracked files inside it.
- [ ] Run `git -C /app/leonardo stash clear`, then click **Undo discard** — it still works.
      (The pinned ref, not the stash stack, is what makes this safe.)
- [ ] Discard twice in a row; **Undo discard** restores the *most recent* one.

**Nothing else moved**

- [ ] Discard with a clean tree ("No changes to discard") leaves no new
      `refs/llamabot/discards` ref and no Undo banner.
- [ ] **Restore** on a checkpoint in History still works, and restored files are still
      editable by Leo afterwards (no root-owned files — same for files brought back by
      Undo: ask Leo to edit one and confirm the edit lands).
- [ ] Save checkpoint, Push to remote and Check for updates all behave as before.

**The safety net fails closed**

- [ ] Optional/advanced: make the snapshot impossible (e.g. `chmod -w` the repo's
      `.git/refs`), click **Discard** — it errors with "could not back up your changes
      first" and the files are all still there, untouched.

## Styled pagination on list pages

Any list page with more than one page of records — e.g. a generated scaffold index
(`bin/rails g scaffold Widget name:string`, seed 60+ rows) or an existing app index.

**The nav looks like the rest of the page**

- [ ] Scroll to the bottom of the list: one row reading `Page 1 of N · <count> total`
      on the left, and numbered page buttons with **Previous**/**Next** on the right —
      bordered white buttons, current page a solid blue chip. No bare blue browser links.
- [ ] Click **Next**, then a numbered page: the table changes and the highlighted chip
      follows the page you are on.
- [ ] On a long list (20+ pages) the numbers gap with `…` instead of running off screen.
- [ ] Narrow the browser to phone width — the nav wraps onto more rows, nothing
      overflows sideways.

**Filters survive paging**

- [ ] Type something in the index search box, apply, then click **Next** — the search
      term is still applied and still in the box (check the URL keeps `q=`).

**Nothing else moved**

- [ ] A list that fits on one page shows no pagination nav at all.
- [ ] A page that calls Pagy's own `pagy_nav` (e.g. an older hand-written index) now
      renders the same styled nav, and its links still work.

## Correct passwords sign in again (CSRF token wipe)

Five separate boxes hit the same lockout: a correct password answers 303, the session
comes back empty, and the user bounces straight to the sign-in page — forever. A wrong
password behaves completely normally, which is why every probe missed it.

Anything that touches `current_user` / `user_signed_in?` from a `before_action` makes
Warden authenticate right out of the sign-in form params. Devise then deletes
`session[:_csrf_token]` as part of that early authentication, and the CSRF check that
runs afterwards rejects a perfectly valid login.

Four things changed, and any one of them alone is enough to keep the box working:

1. `protect_from_forgery ... prepend: true` is now first in the skeleton's
   `ApplicationController`, with `authenticate_user!` moved below it.
2. `touch_last_seen` reads warden passively instead of calling `user_signed_in?`.
3. `clean_up_csrf_token_on_authentication = false` in the skeleton's `devise.rb`, so a
   *future* ordering mistake degrades to "token not rotated" instead of "nobody can log in".
4. llama_bot_rails' activity tracker resolves its actor passively — it is included into
   `ActionController::Base`, so `current_user` there ran ahead of the app's own callbacks.

**Setup**

- Change is in the **LlamaPress-Simple base image** (and its vendored llama_bot_rails) —
  needs a released image, not just a container restart.
- Code: `app/controllers/application_controller.rb`,
  `app/controllers/users/sessions_controller.rb`, `config/initializers/devise.rb`,
  `config/routes.rb`, and the gem's
  `app/controllers/concerns/llama_bot_rails/activity_tracking.rb`.
- Automated coverage: `spec/requests/devise_login_csrf_spec.rb`,
  `spec/requests/csrf_ordering_spec.rb`, and the gem's
  `spec/lib/llama_bot_rails/activity_tracking_actor_spec.rb`.

**Do NOT verify with a wrong password — it passes while the bug is live.**

- [ ] On a box with login enabled, register or pick a real user and note the password.
- [ ] Sign out. Load `/users/sign_in` **over https** (with `assume_ssl` the session
      cookie is Secure, so plain http gives misleading results).
- [ ] Enter the **correct** password and submit. You land on a signed-in page.
- [ ] Reload, then navigate to another page. You are **still signed in** — no bounce
      back to the sign-in form.
- [ ] Sign out and back in a second time; `sign_in_count` should go up by exactly 1 per
      login (it went up by 2 while the bug was live).

**The wrong password still behaves**

- [ ] Submit a deliberately wrong password: you get "Invalid Email or password", stay on
      the form, and are not signed in.

**Activity feed still names the actor**

- [ ] Signed in, create or edit a record (e.g. a contact).
- [ ] Open `/llama_bot/activity` — the new event names **you**, not "Anonymous". This is
      the thing the engine-side fix could have broken.
- [ ] Sign out and submit a public form, if the app has one — that event stays
      "Anonymous" rather than claiming a user.

**Known tradeoff to eyeball**

- [ ] `/users/sign_in` and `/users/sign_up` now use `with: :reset_session`, so a stale
      or missing token there silently resets the session and retries instead of throwing
      a 422 at the user. Leave a login page open for a long while, then submit it — you
      should get signed in (or a normal "Invalid Email or password"), never a raw error
      page. Everything past sign-in still rejects a bad token.

## The feedback bubble shows up on every page

The purple chat bubble in the bottom-right corner is how users report bugs. It only
draws when `window.llamapressConfig.feedbackBubbleEnabled` **and** `.userLoggedIn` are
both true — and that config object was written by a single layout partial that only one
overlay had, and only its `application.html.erb` rendered. So the bubble was silently
absent from every other layout: the `prototypes` layout, admin shells, anything Leo
generated, and the base image's own `application.html.erb`, which never had the block at
all. No error, nothing in the console — just no bubble.

The engine now injects the config into the `<head>` of **every** HTML response instead
(`LlamaBotRails::PageConfigInjection`), so no layout can forget it.

**Setup**

- Change is in the **base image + its vendored llama_bot_rails** — needs a released
  image (or `up -d --force-recreate llamapress` in dev), not just a hard refresh. The
  engine initializer only runs at boot.
- Code: the gem's `app/controllers/concerns/llama_bot_rails/page_config_injection.rb`
  and `lib/llama_bot_rails/engine.rb`; Leonardo's
  `app/views/layouts/_llamapress_page_context.html.erb` loses its now-duplicate copy.
- Notes: the gem's `docs/page_config_injection.md`. Automated coverage: the gem's
  `spec/requests/llama_bot_rails/page_config_injection_spec.rb`.

**The bubble is there — this is the one that matters**

- [ ] Sign in. On the normal home page, the grey/purple bubble is in the bottom-right.
      Click it: the Feedback / Messages / Notifications panel opens.
- [ ] Go to a page that does **not** use the main app layout — an admin screen, a Leo
      generated page, or anything under `/prototypes/...`. The bubble is there too, and
      opens the same panel.
- [ ] Ask Leo to build a brand-new page with its own layout. Load it. The bubble is
      there without anyone wiring anything up.
- [ ] File a piece of feedback from one of those non-standard pages and confirm it lands
      in `/llama_bot/user_feedbacks` with the right page path on it.

**Signed out, no bubble**

- [ ] Sign out and load the same pages: no bubble anywhere (it needs a signed-in user).

**View source spot-check**

- [ ] View source on any page: one `<script>window.llamapressConfig = {...}</script>`
      just after `<head>`, above the importmap. Exactly **one** — search the page and
      confirm there is no second copy.
- [ ] `userLoggedIn` is `true` when signed in and `false` when signed out.

**Nothing else moved**

- [ ] Pages still render normally — no stray markup at the top of the page, no layout
      shift, no console errors.
- [ ] JSON endpoints and Turbo Stream responses are untouched (open something that
      returns JSON, e.g. a `.json` URL — it is still valid JSON, no script tag).
- [ ] File downloads / attachments still download correctly.
- [ ] Leo's own chat, the record drawer, and the releases page all still work.

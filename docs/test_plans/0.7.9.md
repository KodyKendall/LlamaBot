# 0.7.9 manual test plan

Pairs with the automated tests. Automated coverage is listed per item so you only
hand-check what a test cannot reach.

| Change | Repo | Automated |
|---|---|---|
| The click-to-select tool survives a preview reload | LlamaBot | 6 tests, `app/tests/js/element_selector_rearm_on_load.test.mjs` |
| DeepSeek V4.1 Flash (Fireworks) in the dropdown | LlamaBot | 8 tests, `test_model_registry_consistency.py` |
| No raw `function_call` JSON in the chat (ChatGPT/Codex) | LlamaBot | 18 tests, `test_message_invariants.py` + `test_ui_content_is_text_only.py` |
| 👍/👎 clickable while the run is still streaming | LlamaBot | 10 tests, `app/tests/js/feedback_buttons_during_stream.test.mjs` |

The click-to-select fix is frontend-only — a hard refresh picks it up. The other two are
**Python**, so they need `docker compose -f docker-compose-dev.yml up -d --force-recreate
llamabot` (`restart` does not reload, and there is no `--reload` on uvicorn).

**Run the JS suite through its pytest wrapper, in the container** — that is the path CI
uses, and the only one that works there:

```
docker exec -w /app/app leonardo-llamabot-1 python -m pytest tests/test_frontend_element_selector_rearm_js.py -q
```

A bare `node --test` inside the container fails nearly everything: node 18 reads the
imported `app/frontend/*.js` sources as CommonJS, so every named import throws. The
wrapper's `--experimental-default-type=module` flag is what fixes that, which is also why
**a new `tests/js/*.test.mjs` file is invisible to CI until its
`app/tests/test_frontend_<name>_js.py` wrapper exists**. This change adds
`test_frontend_element_selector_rearm_js.py`.

## The click-to-select tool survives a preview reload

Reported from the CRM box (`crm-4`, 2026-09-10): "the little mouse select tool in llamabot
chat.html isn't working on the iframe". The button lit up, nothing highlighted, and it took
three clicks to recover.

The parent posted `enable-element-selector` into the iframe exactly once and never
re-checked that the iframe agreed. Now it re-sends on every iframe `load`.

**What you need:** any box with a Rails app in the preview pane and at least one page with
clickable text. A slow-loading app makes case A much easier to hit.

### A. Click the tool while the preview is still loading

1. Open the chat. In the preview pane, navigate to any page (or ask Leo to make an edit, so
   the frame reloads).
2. **Immediately**, while the page is still visibly loading, click the element-selector
   button (the mouse-pointer icon by the message box).
3. Wait for the page to finish loading.
4. Hover over the page.

- **Expect:** elements highlight on hover, and the button is lit. One click on an element
  drops it into the message box as a badge.
- **Before the fix:** the button was lit but nothing highlighted; the next click turned the
  button off without ever having been on, so you needed three clicks total.

### B. Turn the tool on, then let the preview reload

1. With the preview fully loaded, click the element-selector button. Confirm hovering
   highlights elements.
2. Ask Leo to make any edit to the app, and wait for the preview to reload on its own.
   (Or navigate with the preview's own URL bar — same thing.)
3. Without touching the button, hover over the reloaded page.

- **Expect:** elements still highlight. The button was lit the whole time and it is telling
  the truth.
- **Before the fix:** highlighting was dead after the reload while the button stayed lit.

### C. The tool does not turn itself on behind your back

1. Make sure the element selector is **off** (button not lit).
2. Reload the preview a few times — navigate, or have Leo edit a file.
3. Hover over the page.

- **Expect:** nothing highlights, ever. A reload must not enable a tool you did not ask for.

### D. Turning it off stays off

1. Turn the tool on, then click the button again to turn it off.
2. Let the preview reload.
3. Hover.

- **Expect:** nothing highlights.

### E. Picking an element still ends selection mode

1. Turn the tool on, click an element. It should appear as a badge above the message box
   and the button should go unlit.
2. Let the preview reload.
3. Hover.

- **Expect:** nothing highlights — one pick is one pick. Click the button again to select a
  second element; the badges accumulate (1st, 2nd, ...).

## Known: this box's model tests are red, and it is not this change

`.leonardo/model_policy.json` on a dev box is pushed by the mothership and narrows the
model allowlist, so `is_model_enabled('deepseek-v4-flash')` is False where the repo's tests
expect True. That reds out 50 tests across `test_model_policy.py`,
`test_default_model_policy.py`, `test_model_registry_consistency.py`,
`test_provider_key_never_leaks_openai.py`, `test_openrouter_registry.py` and
`test_custom_agent_modes.py`.

Verified as pre-existing by an A/B on this branch — the same six files report **50 failed /
300 passed** both with this change applied and with it fully removed. Do not chase it from
inside a frontend PR.

## No raw `function_call` JSON in the chat (ChatGPT/Codex path)

Reported from the CRM box (`crm-4`, 2026-09-10) on a thread running **Codex GPT
authenticated with the user's own ChatGPT account** (`gpt-5.6-sol`). An ordinary
assistant bubble read, verbatim:

```
Leonardo Said: {"type": "function_call", "name": "ask_user_question", "arguments": "{...}", "call_id": "call_g9ak...", ...}
```

…and only THEN did the properly formatted question card render underneath it.

**Why.** On the Responses API, `AIMessage.content` is a list of provider *items*, not text
— an assistant turn can be `[reasoning, function_call]` with no text block at all. None of
those types were in `SUPPORTED_BLOCK_TYPES`, so every one was stringified into a text block
carrying its own JSON. Nothing is persisted, but the corrupted history is what the model
*reads*: its own prior tool calls came back to it looking like assistant prose full of
function-call JSON, and GPT-5 imitates the format it is shown. So it emitted that JSON as
literal text, then made the real call — exactly the order the user saw.

**You need:** a box on the ChatGPT/Codex-auth path — a model like `gpt-5.6-sol` with a
connected ChatGPT account (Settings → ChatGPT Account). This does **not** reproduce on the
DeepSeek/Anthropic models, which use the Chat Completions shape.

### A. The reported bubble is gone

1. Open a thread and pick a ChatGPT-authenticated model (`gpt-5.6-sol`).
2. Ask for something that makes Leo ask you a clarifying question — e.g.
   *"Plan a homepage for my consulting site, then check with me before building."*
3. Watch the chat as it answers.

- **Expect:** the question card renders, and nothing else. No bubble containing
  `{"type": "function_call"` or `"call_id"`.
- **Before the fix:** a raw JSON bubble appeared first, then the card.

### B. It still gets worse with thread length — check a long one

The corruption was rewritten on *every* model call, for *every* historical tool call, so it
compounded. Answer the question, then keep going for several more turns with more tool use.

- **Expect:** still no JSON bubbles at turn 10 the way there were at turn 3.

### C. The log flood is gone

```
docker compose -f docker-compose-dev.yml logs --tail=400 llamabot | grep -c "stringifying unsupported content block type"
```

- **Expect:** 0 during normal operation. If a genuinely new provider type shows up you get
  **one** line naming it, then silence — not 40+ identical lines inside one second.

### D. Reasoning continuity is intact (the thing we must not have broken)

`reasoning` blocks carry `encrypted_content`, which gpt-5.x needs to continue its own
reasoning across turns. Dropping them would have been the easy wrong fix.

1. On the same ChatGPT model, give Leo a multi-step task that spans several turns.
2. Let it run 4–5 turns.

- **Expect:** normal behaviour — no "I don't have context", no restarts from scratch, no
  provider 400 about reasoning items.

### E. Tool calls still execute

1. Ask for something that writes a file.

- **Expect:** the tool runs and reports back as usual. `function_call` items are how this
  API expresses a call it will later be handed a `function_call_output` for; stripping them
  would break the "tool_calls not followed by tool messages" invariant.

### F. The mothership stores readable text

If you have mothership access, open `/admin/message_annotations` for a thread from this
box.

- **Expect:** assistant content reads as prose.
- **Before:** the Python repr of the whole block list
  (`"[{'type': 'text', 'text': ...}]"`), which also made the eval miners useless on this
  path.

## DeepSeek V4.1 Flash (Fireworks)

**You need:** `FIREWORKS_DEEPSEEK_API_KEY` (or `FIREWORKS_API_KEY`) on the box. Without it
the option is correctly greyed out, which is itself worth one check.

1. Settings → confirm the key is present, then reload the chat.
2. Pick **DeepSeek V4.1 Flash (Fireworks)** in the model dropdown and send a message.
   - **Expect:** a normal reply. If you get an auth error mentioning `api.deepseek.com`,
     the Fireworks key went to the wrong host — that is the `api_base` trap the tests pin.
3. Attach an **image** and ask about it.
   - **Expect:** it reads the image. V4.1 is the first DeepSeek entry that is not
     text-only, and the frontend seeds `images: true` so the upload is not auto-switched to
     Gemini before `/api/available-models` resolves.

   - **Expect:** it is not offered/accepted for this model — PDF is deliberately off.
5. Confirm **DeepSeek V4 Flash (Fireworks)** (the older sibling) still works.
   - **Expect:** unchanged. The new entry is a sibling, not a re-point; boxes that picked
     V4 must not silently migrate onto V4.1.

## 👍/👎 while the run is still streaming

Asked for by Darren: *"the thumbs down/thumbs up only works AFTER the messages/stream has
stopped, but I want them to show up as available ... even when it's still running."* The
best moment to rate a reply is the moment it goes wrong, which is mid-run — by the time the
stream ends the user has moved on, and every rating lost there is an eval signal we never
get.

The bubble is now split: `[data-llamabot="message-body"]` holds the streamed text and is
rewritten on every chunk, `[data-llamabot="message-actions"]` holds copy/👍/👎/reply and is
built once. Frontend-only — a hard refresh picks it up.

### A. The buttons are there before the text is

1. Send a prompt that produces a long answer (*"explain how the feedback system works, in
   detail"*).
2. **As soon as the first words appear**, hover the bubble.

- **Expect:** copy, 👍, 👎 and reply are all visible and clickable.
- **Before:** nothing until the whole run finished.

### B. They survive the whole stream — the real regression

Keep hovering as the text grows. The bubble re-renders on *every* chunk.

- **Expect:** the buttons stay put. No flicker, no disappearing and reappearing.
- This is the bit that breaks if the text ever gets written to the bubble instead of to
  `message-body`.

### C. A mid-stream rating lands, and lands on the right message

1. While the answer is **still streaming**, click 👎 and type a short note.
2. Let the run finish.
3. Check the mothership annotation (or the network tab): `POST /api/feedback`.

- **Expect:** `scope: "message"`, a **non-empty `message_key`**, and the note.
- **Why it matters:** mid-stream the text is half-written, so content matching cannot
  identify the row — that is how 4% of end-user annotations ended up on fabricated
  placeholder rows (annotation #688). The key is what makes it land.
- **Note:** the mothership half is Mother Leo's — `resolve_feedback_message` still matches
  on content today, so until that lands a mid-stream rating resolves the old way. This
  change is safe on its own; the two together are what make an early rating land right.

### D. No duplicate control rows

1. Rate mid-stream, then let the run end.

- **Expect:** still exactly one copy button and one pair of thumbs. Not two rows.
- `finalizeAiMessages()` still sweeps at end of stream as a backstop; it must be a no-op
  here.

### E. Stream resume does not duplicate them either

1. Start a long answer. Kill the network (devtools offline) for ~10s mid-answer, then
   restore it so the stream resumes.

- **Expect:** the bubble is rewritten with the full authoritative text, and there is still
  exactly one control row.

### F. Copy and reply still work

1. Click copy on a finished message → paste somewhere.
   - **Expect:** the raw markdown, not rendered HTML. (`data-raw-content` stays on the outer
     bubble; moving it into the body would break copy, reply and the transcript builder.)
2. Click reply → the quote preview appears above the input.

### G. An empty bubble still disappears

Some turns open a bubble and then produce only a tool call, no text.

- **Expect:** no stray empty bubble with a lonely button row left in the transcript. (The
  "did any text arrive?" check reads `data-raw-content` now — reading `innerHTML` would
  never be empty again, since the control row is always there.)

### H. Known gap — tool/plan bubbles are still unratable

Darren asked for "any annotation". Tool-call and plan bubbles are **not** included in this
change: they toggle open/closed via an inline `onclick` on a wrapper around their whole
body, so a thumbs-click would also expand/collapse the panel — a delegated handler cannot
stop an inline one that already ran. That needs its own change and its own tests.

- **Expect:** tool bubbles behave exactly as before — no buttons, toggle still works.

## Feedback bubble: element picker on touch, and the annotator's shape tools

Reported by Nicole Haldis (sipstaff.com) and Jennie Morgan (goconnexa.com) on box
`leo-borro`, 2026-09-11: the pointer / select-element icon in the purple feedback bubble
"wasn't working" on Safari on an iPhone and on a second non-Chrome browser, and the tool
generally was "not a very good user experience".

Both files ship to the fleet through `bin/update`'s allowlist
(`rails/app/javascript/llamapress/`), so a merged change reaches a box on its next update —
but it still has to ride a release the fleet is actually pushed.

### I. The element picker on a REAL phone (the part a unit test cannot prove)

iOS Safari is the engine that matters here and no CI tier has one. Do this on an actual
iPhone, or in the iOS Simulator, against a Leo-built page with plain `<p>`/`<div>` content
(not links, not buttons — the old code depended on WebKit synthesising a click, which it
does not do for non-interactive elements).

1. Open the purple feedback bubble → tap the pointer / select-element icon.
   - **Expect:** the feedback panel closes AND a purple banner appears across the top
     reading "Tap the part of the page you want to point at", with **Use this** (greyed)
     and **Cancel** buttons. Before this change the screen showed *nothing* — that was the
     whole "it wasn't working" report.
2. Tap a plain paragraph.
   - **Expect:** it gets a green outline. Nothing is attached yet. The banner now reads
     "Tap again or 'Use this' to attach this element" and **Use this** is enabled.
3. Tap a *different* paragraph.
   - **Expect:** the green outline moves. Still nothing attached. (There is no hover on a
     finger — committing on the first tap would attach whatever the finger landed on.)
4. Tap the same paragraph a second time.
   - **Expect:** the banner disappears, the feedback panel reopens with the element
     attached in the preview row.
5. Repeat step 2, then tap **Use this** instead.
   - **Expect:** same result as step 4.
6. Arm the picker again and tap **Cancel**.
   - **Expect:** the banner goes, the feedback panel reopens, nothing attached. This is the
     one that must work: before, Escape was the only exit and an iPhone has no Escape key,
     so a mis-tap left the user in an invisible mode with no way out but a reload.
7. Arm the picker and try to drag/scroll the page.
   - **Expect:** the page does not scroll out from under you while armed.
8. Arm the picker and tap a **link**.
   - **Expect:** the link is attached as the selection; the browser does **not** navigate.
9. Repeat 1–6 in the second browser Nicole and Jennie use (Samsung Internet, or whichever
   "internet browser" they confirm).

### J. The element picker on a desktop mouse — nothing may have changed

1. Arm the picker and move the mouse around.
   - **Expect:** the green outline follows the cursor, as before.
2. Click once.
   - **Expect:** it attaches immediately — no confirm step for a mouse.
3. Arm it again and press Escape.
   - **Expect:** cancelled, panel reopens. Escape still works.
4. Confirm the banner never gets picked: hover and click the banner itself.
   - **Expect:** nothing is attached, and the buttons still respond.

### K. The annotator's shape tools

Camera icon → drag a region → the "Annotate Screenshot" modal.

1. Arrow tool. Draw an arrow. Now draw a second arrow **starting on top of the first one**.
   - **Expect:** two arrows. Before, the second drew nothing and the first got dragged
     across the screenshot instead (an arrow's hit area is the whole box its diagonal
     spans — a modest arrow claimed roughly 183x123 px of dead zone).
2. Rectangle tool, starting on top of an existing arrow. Then text, on top of one.
   - **Expect:** both land. Same bug, same three lines.
3. Arrow tool, single click with no drag.
   - **Expect:** a short arrow appears. Before: nothing at all, which reads as broken.
4. Pick a drawing tool and try to drag an annotation you already made.
   - **Expect:** it does not move — you draw instead. That is deliberate.
5. Click the new **Move** tool (the four-way arrows, right of Text), then drag an
   annotation.
   - **Expect:** it moves and can be resized. This is the way back.
6. Undo, colour picker, pen, and **Attach** → check the PNG that lands on the feedback
   form.
   - **Expect:** every annotation is in the exported image, including the non-selectable
     ones.

### L. Two findings NOT addressed here — decide separately

Read out of the code, not reproduced; each changes behaviour enough to want its own call:

- `captureRegion` calls `navigator.mediaDevices.getDisplayMedia`, so desktop Chrome shows
  its "Choose what to share" dialog before anyone can send feedback; dismissing it falls
  back to `html2canvas` silently, and Firefox/Safari differ again. iOS Safari very likely
  does not support it at all, which would mean every mobile capture already takes the
  html2canvas path. Worth asking whether the prompt earns its place.
- Cancelling the screenshot (the overlay's Cancel, or the modal's Cancel/X) leaves the
  feedback panel shut — the panel is only reopened by the attach callback. The typed text
  survives in the DOM, so nothing is lost; it just looks like the widget quit. Same shape
  as the element-picker defect fixed above.

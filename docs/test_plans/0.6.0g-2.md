## Friction reporting (`report_friction` — Leos can complain about their own tools)

Leos hit papercuts constantly — a tool erroring in a way its description never warned
about, a root-owned file they can't edit, output that contradicts the docs — and none of
it raised anything, so it died in the transcript and we only heard about it secondhand.
Every mode now has a `report_friction` tool that files a short structured complaint down
the existing error pipeline, tagged `source="agent_friction"`.

The unusual thing to QA here: **the user should see nothing.** Most of this checklist is
confirming the feature is invisible and harmless from the chat, and visible only in the
logs and the mothership queue.

**Setup**

- Box: https://llamapress-dev.llamapress.ai (or any box on this build).
- This is a **Python** change — uvicorn runs without `--reload` on this box, so a hard
  refresh is NOT enough. Force-recreate first, or you'll QA stale code and get a false
  pass:
  ```bash
  cd ~/dev/Leonardo && docker compose -f docker-compose-dev.yml up -d --force-recreate llamabot
  ```
- Keep a log tail open in a second terminal for the whole run:
  ```bash
  docker compose -f docker-compose-dev.yml logs -f llamabot | grep -i friction
  ```
- Code: `app/agents/leonardo/friction.py`, wired in each mode's `nodes.py`.
  Automated coverage: `app/tests/test_report_friction.py`. Design notes:
  `docs/dev/error_telemetry.md` §4b.

### How to manufacture friction on purpose

The cleanest reproducible papercut is a file the agent can't write. From the dev box:

```bash
docker exec -u root leonardo-llamapress-1 chown root:root /rails/app/models/application_record.rb
```

Then ask Leo, in chat: *"Add a comment at the top of app/models/application_record.rb."*
Undo afterwards:

```bash
docker exec -u root leonardo-llamapress-1 chown 1000:1000 /rails/app/models/application_record.rb
```

### The agent reaches for it unprompted

- [ ] In **Engineer** mode, run the permission repro above. Leo hits the write failure and
      calls `report_friction` on its own — without you naming the tool. Confirm a
      `Reported agent friction: AgentFriction.permissions` line in the log tail.
- [ ] The same run still **finishes the actual task** (or explains why it can't). Reporting
      is not where the turn ends.
- [ ] Ask directly in any mode: *"Report friction: the bash tool's output gets truncated
      with no marker."* It files one, and the log line shows
      `AgentFriction.confusing_output` (or a near category — the exact category is the
      agent's judgement call, not a pass/fail).

### It's in every mode

One quick run per mode. Fastest prompt that works in all of them: *"Use your
report_friction tool to file a test papercut about anything you've noticed."*

- [ ] **Engineer** — files a report (log line appears).
- [ ] **Engineer + Plan toggle** — files a report.
- [ ] **Beginner** — files a report. (Most important of the six: beginner mode binds its
      tools from a separate list, so this is the one most likely to be missing.)
- [ ] **Beginner + Plan toggle** — files a report.
- [ ] **Ticket** — files a report.
- [ ] **Ticket + Plan toggle** — files a report.

### The user sees nothing

- [ ] Across every run above: Leo **never mentions** filing a report in its chat reply, and
      never apologises for the friction. If it says something like "I've reported this to
      the team", that's a prompt failure — note it here.
- [ ] The tool call shows in the tool-call stream like any other (that's fine and expected)
      — but nothing appears in the message body, no banner, no toast.
- [ ] Leo doesn't **stop and wait** after reporting. The next thing it does is the work.

### It never breaks the turn

- [ ] Ask: *"Call report_friction with category 'banana' and severity 'catastrophic'."*
      It succeeds anyway — no tool error, no retry loop. (Bad values are snapped to
      `other` / `annoyance`.)
- [ ] Ask Leo to report a papercut with a very large pasted error blob (dump a long log
      into it). The turn completes normally; nothing hangs.
- [ ] Watch the response time on a turn that files a report. It should feel identical to
      one that doesn't — the network send is detached, so the agent never waits on it.

### Dedupe and the per-conversation cap

- [ ] In one conversation, ask Leo to report **the same** papercut twice. The second one is
      dropped — only one `Reported agent friction` line in the log, and Leo isn't told it
      failed.
- [ ] In one conversation, ask for **four different** papercuts. Only the first three send;
      the fourth returns a "budget used up" message and Leo carries on regardless.
- [ ] Open a **new thread** (new conversation) and report again. It sends — the cap is per
      conversation, not global.

### Delivery — against the local stub (works on the dev box)

The dev box's `instance.json` has an empty token, so `MothershipClient.enabled` is false
and reports are built and then dropped before the network. `scripts/mothership_stub.py`
stands in for llamapress.ai so the wire format can still be checked here — see its
docstring for the instance.json edit and the force-recreate. **Put instance.json back
(empty token) when you're done.**

- [ ] Start the stub on the host, point the box at it, force-recreate llamabot. File a
      friction report from chat and watch the POST print in the stub's terminal.
- [ ] The printed body has `source: "agent_friction"` and
      `error_class: "AgentFriction.<category>"`.
- [ ] It carries `model`, `agent_mode`, `llamabot_version` and `thread_id`, and the
      `traceback` field holds the severity, the tool name and the verbatim `evidence`.
- [ ] A `blocked`-severity report shows `recovered: false`; `workaround`/`annoyance`
      shows `true`.
- [ ] Stop the stub mid-session and file another report. The chat turn completes exactly
      as normal — the send fails soft with one warning line in the llamabot log.

### Delivery to the real mothership — needs a managed Leo box

Only this proves the *receiver* works. Blocked until the mothership does its part —
see `docs/handoff_mothership_agent_friction.md`.

- [ ] On a managed box, file a report and confirm it lands in the mothership **Error
      Queue** as a new row.
- [ ] The row's `error_class` reads `AgentFriction.<category>` — so friction is one filter
      away from real crashes even before the mothership learns the new `source` value.
- [ ] The row carries the **model** and **agent mode**, and the traceback field holds the
      severity, the tool name, and the verbatim error text the agent pasted into
      `evidence`.
- [ ] A `blocked`-severity report shows `recovered = false`; a `workaround` or `annoyance`
      one shows `true`.
- [ ] **Known gap until the mothership ships its side:** the row's `source` will read
      `llamabot`, not `agent_friction`. The mothership allowlists `source` to
      `%w[llamabot rails_app frontend]` and silently defaults anything else. Confirm it's
      *only* the label that's wrong and the rest of the row is right.

### Degrades safely

- [ ] On the dev box (no `instance.json`), file a report. The log shows
      `Friction report dropped: mothership integration disabled` — and the chat turn is
      completely unaffected.
- [ ] Cut the box's outbound network (or point `mothership_url` at a dead host) and file a
      report. The turn still completes normally and the failure is a single warning line in
      the log, nothing more.

### Sub-agents

- [ ] Ask for something big enough that Leo delegates (*"research how tickets are stored
      and summarise"*). If a sub-agent hits friction, its report appears in the log the
      same way — and it draws from the **same** three-report budget as the parent
      conversation, not a fresh one.

## Friction reporting (`report_friction` — Leos can complain about their own tools)

Leos hit papercuts constantly — a tool erroring in a way its description never warned
about, a root-owned file they can't edit, output that contradicts the docs — and none of
it raised anything, so it died in the transcript and we only heard about it secondhand.
Every mode now has a `report_friction` tool that files a short structured complaint down
the existing error pipeline, tagged `source="agent_friction"`.

The unusual thing to QA here: **the user should see nothing.** Most of this checklist is
confirming the feature is invisible and harmless from the chat, and visible only in the
logs and the mothership queue.

**Setup**

- Box: https://llamapress-dev.llamapress.ai (or any box on this build).
- This is a **Python** change — uvicorn runs without `--reload` on this box, so a hard
  refresh is NOT enough. Force-recreate first, or you'll QA stale code and get a false
  pass:
  ```bash
  cd ~/dev/Leonardo && docker compose -f docker-compose-dev.yml up -d --force-recreate llamabot
  ```
- Keep a log tail open in a second terminal for the whole run:
  ```bash
  docker compose -f docker-compose-dev.yml logs -f llamabot | grep -i friction
  ```
- Code: `app/agents/leonardo/friction.py`, wired in each mode's `nodes.py`.
  Automated coverage: `app/tests/test_report_friction.py`. Design notes:
  `docs/dev/error_telemetry.md` §4b.

### How to manufacture friction on purpose

The cleanest reproducible papercut is a file the agent can't write. From the dev box:

```bash
docker exec -u root leonardo-llamapress-1 chown root:root /rails/app/models/application_record.rb
```

Then ask Leo, in chat: *"Add a comment at the top of app/models/application_record.rb."*
Undo afterwards:

```bash
docker exec -u root leonardo-llamapress-1 chown 1000:1000 /rails/app/models/application_record.rb
```

### The agent reaches for it unprompted

- [ ] In **Engineer** mode, run the permission repro above. Leo hits the write failure and
      calls `report_friction` on its own — without you naming the tool. Confirm a
      `Reported agent friction: AgentFriction.permissions` line in the log tail.
- [ ] The same run still **finishes the actual task** (or explains why it can't). Reporting
      is not where the turn ends.
- [ ] Ask directly in any mode: *"Report friction: the bash tool's output gets truncated
      with no marker."* It files one, and the log line shows
      `AgentFriction.confusing_output` (or a near category — the exact category is the
      agent's judgement call, not a pass/fail).

### It's in every mode

One quick run per mode. Fastest prompt that works in all of them: *"Use your
report_friction tool to file a test papercut about anything you've noticed."*

- [ ] **Engineer** — files a report (log line appears).
- [ ] **Engineer + Plan toggle** — files a report.
- [ ] **Beginner** — files a report. (Most important of the six: beginner mode binds its
      tools from a separate list, so this is the one most likely to be missing.)
- [ ] **Beginner + Plan toggle** — files a report.
- [ ] **Ticket** — files a report.
- [ ] **Ticket + Plan toggle** — files a report.

### The user sees nothing

- [ ] Across every run above: Leo **never mentions** filing a report in its chat reply, and
      never apologises for the friction. If it says something like "I've reported this to
      the team", that's a prompt failure — note it here.
- [ ] The tool call shows in the tool-call stream like any other (that's fine and expected)
      — but nothing appears in the message body, no banner, no toast.
- [ ] Leo doesn't **stop and wait** after reporting. The next thing it does is the work.

### It never breaks the turn

- [ ] Ask: *"Call report_friction with category 'banana' and severity 'catastrophic'."*
      It succeeds anyway — no tool error, no retry loop. (Bad values are snapped to
      `other` / `annoyance`.)
- [ ] Ask Leo to report a papercut with a very large pasted error blob (dump a long log
      into it). The turn completes normally; nothing hangs.
- [ ] Watch the response time on a turn that files a report. It should feel identical to
      one that doesn't — the network send is detached, so the agent never waits on it.

### Dedupe and the per-conversation cap

- [ ] In one conversation, ask Leo to report **the same** papercut twice. The second one is
      dropped — only one `Reported agent friction` line in the log, and Leo isn't told it
      failed.
- [ ] In one conversation, ask for **four different** papercuts. Only the first three send;
      the fourth returns a "budget used up" message and Leo carries on regardless.
- [ ] Open a **new thread** (new conversation) and report again. It sends — the cap is per
      conversation, not global.

### Delivery — against the local stub (works on the dev box)

The dev box's `instance.json` has an empty token, so `MothershipClient.enabled` is false
and reports are built and then dropped before the network. `scripts/mothership_stub.py`
stands in for llamapress.ai so the wire format can still be checked here — see its
docstring for the instance.json edit and the force-recreate. **Put instance.json back
(empty token) when you're done.**

- [ ] Start the stub on the host, point the box at it, force-recreate llamabot. File a
      friction report from chat and watch the POST print in the stub's terminal.
- [ ] The printed body has `source: "agent_friction"` and
      `error_class: "AgentFriction.<category>"`.
- [ ] It carries `model`, `agent_mode`, `llamabot_version` and `thread_id`, and the
      `traceback` field holds the severity, the tool name and the verbatim `evidence`.
- [ ] A `blocked`-severity report shows `recovered: false`; `workaround`/`annoyance`
      shows `true`.
- [ ] Stop the stub mid-session and file another report. The chat turn completes exactly
      as normal — the send fails soft with one warning line in the llamabot log.

### Delivery to the real mothership — needs a managed Leo box

Only this proves the *receiver* works. Blocked until the mothership does its part —
see `docs/handoff_mothership_agent_friction.md`.

- [ ] On a managed box, file a report and confirm it lands in the mothership **Error
      Queue** as a new row.
- [ ] The row's `error_class` reads `AgentFriction.<category>` — so friction is one filter
      away from real crashes even before the mothership learns the new `source` value.
- [ ] The row carries the **model** and **agent mode**, and the traceback field holds the
      severity, the tool name, and the verbatim error text the agent pasted into
      `evidence`.
- [ ] A `blocked`-severity report shows `recovered = false`; a `workaround` or `annoyance`
      one shows `true`.
- [ ] **Known gap until the mothership ships its side:** the row's `source` will read
      `llamabot`, not `agent_friction`. The mothership allowlists `source` to
      `%w[llamabot rails_app frontend]` and silently defaults anything else. Confirm it's
      *only* the label that's wrong and the rest of the row is right.

### Degrades safely

- [ ] On the dev box (no `instance.json`), file a report. The log shows
      `Friction report dropped: mothership integration disabled` — and the chat turn is
      completely unaffected.
- [ ] Cut the box's outbound network (or point `mothership_url` at a dead host) and file a
      report. The turn still completes normally and the failure is a single warning line in
      the log, nothing more.

### Sub-agents

- [ ] Ask for something big enough that Leo delegates (*"research how tickets are stored
      and summarise"*). If a sub-agent hits friction, its report appears in the log the
      same way — and it draws from the **same** three-report budget as the parent
      conversation, not a fresh one.

## Oversized page payloads / the summarization loop (SupportIncident #246)

A customer's thread got stuck summarizing on every step and never completed a turn. Chatting
from a content-heavy page sent the **entire rendered page** (10.6 MB) with every message, and
picking an element on that page put a 375 KB block of HTML inside the message itself — and
compaction could never reclaim either. Nothing here is user-visible when it works; QA is
mostly confirming the payloads got small and nothing about chatting got worse.

**Setup**

- Box: https://llamapress-dev.llamapress.ai (or any box on this build).
- **Python + JS change.** Force-recreate llamabot (uvicorn has no `--reload` here) *and*
  hard-refresh the browser, or you will QA stale code:
  ```bash
  cd ~/dev/Leonardo && docker compose -f docker-compose-dev.yml up -d --force-recreate llamabot
  ```
- Build a heavy page to test with: ask Leo for a page that renders a few thousand rows of
  text (*"make me a /transcripts page with 3000 rows of lorem ipsum"*). You need it to be
  genuinely big — a normal page won't trip any of this.
- Keep a log tail open:
  ```bash
  docker compose -f docker-compose-dev.yml logs -f llamabot | grep -aiE "capped|truncat|trigger"
  ```

### The payload actually got small

- [ ] Open the heavy page in the preview and send a normal chat message from it. Then run
      the triage one-liner — the longest log line should be **tens of KB, not megabytes**:
      ```bash
      docker compose -f docker-compose-dev.yml logs llamabot --since 10m 2>&1 \
        | grep -a "Received message:" | wc -L
      ```
- [ ] The log shows a `Capped oversized inbound field debug_info.full_html: … -> … bytes`
      warning naming the field and both sizes.
- [ ] Use the **element picker** on a huge element of that page (a container with thousands
      of rows) and send it. The message still works, and Leo's reply shows it understood
      *which* element you picked.
- [ ] The picked element in the chat transcript carries a visible
      `[truncated: N bytes omitted]` marker — you can tell it's a partial element, not
      broken HTML.

### Nothing normal got worse

- [ ] On an ordinary (small) page, pick a button and ask Leo to change it. It works exactly
      as before, and there is **no** truncation marker anywhere.
- [ ] Ask Leo *"what page am I on?"* from the heavy page — it still answers with the right
      path. (`view_path` / `request_path` must survive the cap; they're what the agent
      actually reads.)
- [ ] Attach a screenshot to a message from the heavy page. The image is unaffected by the
      text cap and Leo describes it correctly.

### A long conversation still recovers

- [ ] Have a genuinely long conversation on the heavy page — enough turns to trigger
      compaction (watch for `RailsSummarizationMiddleware` in the log). After it compacts,
      **the next turn does real work** instead of compacting again. This is the whole bug:
      before the fix it summarized forever and the customer had to abandon the thread.
- [ ] The context wheel drops after compaction and stays down.
- [ ] Leo still knows what you originally asked for after compaction (the first messages are
      preserved — truncated if they were huge, but the *intent* is still there).

### The rescue lever

- [ ] In a thread that has a giant element in it, type `/compact`. It reports
      *"Also truncated N oversized message(s)…"* and the thread keeps working afterwards.

### The thread never wedges, whatever is in it

The point of this one: there is now a hard ceiling on what gets sent to the model. If the
conversation can't be compacted any other way, attachments are dropped, then whole messages,
down to a lone summary — because a thread that loses its screenshots still works and a thread
that loops doesn't.

- [ ] Load a thread up the hard way: paste in large elements from the heavy page, attach a
      couple of screenshots, and keep going for many turns. It keeps answering. It never
      sits in a permanent "thinking" state.
- [ ] After it has had to force things down, Leo says so in its reply (some earlier content
      was dropped) rather than answering confidently from a conversation with holes in it.
- [ ] Screenshots you attached long ago may stop being visible to Leo in a very long thread —
      that's the ladder working. Asking for a fresh screenshot works normally.

### Fails loud, not silently

- [ ] If a thread ever does end up uncompactable, the log carries an **ERROR** line reading
      `summarization did NOT get under the trigger` with the before/after counts and the
      largest message — and the chat keeps working anyway. (Hard to force by hand; if you
      never see this line, that's the expected outcome, not a missed step.)

## `/cookbook` — search the published recipes from the chat box

The cookbook at llamapress.ai/cookbook was only reachable by the agent (it curls
`cookbook.json` when it happens to recognize a pattern) — the user had no way to see what
recipes exist. Typing `/cookbook` in the composer now lists every published recipe, and
anything typed after it filters them. Picking one fills the composer with a directive
naming the recipe; it does **not** send, so you can add your own context first.

**Setup**

- This touches Python (`/api/cookbook` in `app/routers/api.py`) as well as the frontend, so
  force-recreate — a hard refresh alone will QA stale backend code:
  ```bash
  cd ~/dev/Leonardo && docker compose -f docker-compose-dev.yml up -d --force-recreate llamabot
  ```
- Code: `app/frontend/chat/ui/SlashCommandManager.js`, `app/routers/api.py`.
  Automated coverage: `app/tests/js/cookbook_slash_command.test.mjs`,
  `app/tests/test_cookbook_api.py`.

### The list

- [ ] Type `/` — a **Cookbook** section appears in the slash menu with a `/cookbook` entry,
      between the commands and the skills.
- [ ] Pick it (or type `/cookbook`) — the menu fills with real recipes (~28 today), each
      showing its title, a category chip (Auth, Tables, Files…) and a summary underneath.
      The header reads "Cookbook · N recipes".
- [ ] The panel is **tall** (roughly 60% of the window, ~6 recipes at a time) and scrolls
      inside itself — the recipe list must not feel cut off after three rows.
- [ ] Every row is the same height: long titles get the full width and long summaries stop
      at two lines with an ellipsis (hover shows the whole thing). Nothing runs off the row.
- [ ] Filter down to two results — the panel shrinks to fit them instead of leaving a tall
      empty box. Then clear back to `/` — the plain command menu is back to its normal
      short height, not stuck tall.

### The search

- [ ] Keep typing: `/cookbook pdf` narrows the list to PDF recipes. **The menu stays open
      past the space** — every other slash command closes there, this one doesn't.
- [ ] Two words narrow further rather than widening (`/cookbook table export`).
- [ ] Searching a category (`/cookbook auth`) and a tag (`/cookbook devise`) both work, not
      just the title.
- [ ] A query matching nothing says *"No recipes match…"* instead of closing the menu.
- [ ] Arrow keys move through the results and Enter picks the highlighted one.

### Picking one

- [ ] Click a recipe (or press Enter on it). The composer fills with
      *Follow the LlamaPress cookbook recipe "…" — curl https://llamapress.ai/cookbook/<slug>.json …*
      and nothing is sent. The cursor sits at the end so you can add "…on my invoices page".
- [ ] Send it — Leo curls the recipe and follows it, rather than inventing an approach.
- [ ] The ↗ icon on a row opens that recipe on llamapress.ai in a new tab **without** filling
      the composer or closing the chat.

### It degrades quietly

- [ ] Nothing here executes on the box: picking a recipe never shows the "Execute Command"
      confirmation modal and never appears in `/history`.
- [ ] On a phone-width window the list is still tall enough to browse (about half the
      screen) and the rows keep the same title-over-summary shape.

# 0.7.8 manual test plan

Pairs with the automated tests. Automated coverage is listed per item so you only
hand-check what a test cannot reach.

| Change | Repo | Automated |
|---|---|---|
| A 404 stops handing strangers the route table | llama_bot_rails (+ skeleton submodule bump) | 13 specs, `spec/lib/llama_bot_rails/detailed_exceptions_guard_spec.rb` |
| A new thread keeps your chosen model | LlamaBot | 9 tests, `app/tests/js/new_thread_keeps_chosen_model.test.mjs` |
| A default is never saved as your preference | LlamaBot | covered by the same 9 |

The 404 fix ships in the **gem**, so it needs a submodule bump in LlamaPress-Simple and a
new skeleton image before any box gets it. The model fixes are frontend-only — a hard
refresh picks them up, no container restart.

**Run the JS suites through their pytest wrappers, in the container** — that is the path
CI uses, and it is the only one that works there:

```
docker exec -w /app/app leonardo-llamabot-1 python -m pytest tests/test_frontend_*_js.py -q
```

A bare `node --test tests/js/` inside the container fails nearly everything: node 18 reads
the imported `app/frontend/*.js` sources as CommonJS, so every named import throws. The
wrapper's `--experimental-default-type=module` flag is what fixes that, which is also why
**a new `tests/js/*.test.mjs` file is invisible to CI until its
`app/tests/test_frontend_<name>_js.py` wrapper exists**. This change adds
`test_frontend_new_thread_model_js.py`.

Host node 22 can run the `.mjs` files directly, but reports 8 host-only failures
(`leo_diagnostics`, `restart_midrun_reconnect`) that nobody else will ever see. If a host
run goes red, re-check it in the container before believing it.

## 1. A stranger hitting a bad URL gets a plain 404

The bug: Leo boxes run `RAILS_ENV=development` on purpose, so
`consider_all_requests_local` was true for **everyone**. Any unrouted request returned
the ~100 KB Rails developer error page to an anonymous visitor — including the customer
app's entire route table (368 routes on `qa-candidate`, `/admin/users/:id/impersonate`
among them), the engine's file layout and the request env dump. No session, no token, no
header needed, while WordPress scanners were walking the fleet.

**The trap this plan exists to avoid:** the specs run in `RAILS_ENV=test` while the site
runs in `development`. A green suite proves nothing here. Every check below must be run
with `curl` against the **public** URL — not a browser tab you are already signed into,
and not the test suite. This is the same trap as SI#418.

### 1.1 Anonymous — the check that matters

From a machine that has never signed into the box (or just use `curl`, which carries no
cookies):

```
curl -s -o /tmp/404.html -w "%{http_code} %{size_download}\n" \
  https://rails-<box>.leo.llamapress.ai/no-such-path-xyz
grep -c 'impersonate\|route_table' /tmp/404.html
```

- [ ] Status is **404** and the size is **~1.7 KB**, not ~100 KB.
- [ ] The grep prints **0**.
- [ ] Opening `/tmp/404.html` shows the plain "The page you were looking for doesn't
      exist (404)" page — no route list, no source extract, no env dump.

Measured on `llamapress-dev` before/after: **100,025 bytes → 1,722 bytes**, leak markers
32 → 0.

### 1.2 Signed in — you must NOT have lost the debug page

Sign in to the box's Rails app as a normal user, then, in that same browser:

- [ ] Visit `/no-such-path-xyz`. You still get the **full developer error page with the
      route table**. (Measured: 100,214 bytes, 32 markers.)
- [ ] Trigger a real application error (e.g. ask Leo to write a controller action that
      raises). You still get the full debug page with the backtrace and source extract.

If either of these shows the plain page, the guard is too aggressive — that is a
regression, not a fix.

### 1.3 Leo's debug loop still works

Leo reads crashes from the errors feed, not from the HTML page, so this should be
unaffected. Confirm it anyway:

- [ ] Ask Leo to write code that crashes a page, then ask it to fix it. It should notice
      the crash mid-turn and repair it, exactly as in 0.7.4.
- [ ] `curl -s -o /dev/null -w "%{http_code}\n" https://rails-<box>.leo.llamapress.ai/llama_bot/errors`
      returns **403** (alive and agent-gated), not 404 or 500.

### 1.4 Sanity — development mode is still on

- [ ] Editing a view on the box still takes effect without a restart. (If this broke,
      something other than the exception flag got changed.)

## Notes for the reviewer

- **Placement.** The guard is inserted **after** `ActionDispatch::DebugExceptions`, which
  in a Rack stack means *inside* it. The ticket suggested "before"; before puts it
  outside, where DebugExceptions has already rendered the page by the time the exception
  arrives. `bundle exec rails middleware` should show `DebugExceptions` above
  `LlamaBotRails::DetailedExceptionsGuard`.
- **No IP or header trust.** An earlier draft also allowed loopback/private-IP requests
  to see details, so the agent kept the HTML page. That was dropped: it would have rested
  on Caddy always setting `X-Forwarded-For`, and the agent does not need the HTML page.
  Trust is a signed-in session and nothing else — there is no header an attacker can send
  to get the detailed page back.
- **It only ever narrows.** An app already running with `consider_all_requests_local =
  false` keeps that; being signed in never turns details back on.
- **Still open, not in this change:** `rack-attack (6.8.0)` is bundled on every box with
  no initializer. The ticket suggests shipping one (throttle by IP; hard-block `wp-json`,
  `wp-admin`, `wp-login.php`, `.env`, `.git/config`). That is a separate ticket.

## 2. A new thread keeps the model you chose

The bug: the `createNewThread` handler called `setModel(this.defaultTextModel)`
unconditionally, and `setModel()` writes the `llmModel` cookie. So every new thread threw
away the user's model **and** saved the box default as their preference. Reported from
`rsb-dev` 2026-09-03: "You can see it is referring to Chat since I was using Luna but it
says DeepSeek in the dropdown."

The handler's comment called it "user-initiated", but the event has three dispatchers and
**two fire from the agent** mid-conversation, then auto-send the user's text on the new
thread. Those two are the ones to test — the button was never the interesting case.

### 2.1 The New thread button (the case that was already visible)

1. Pick a non-default model in the dropdown. Note which one.
2. Send a message so the thread is real.
3. Click **New thread**.

- [ ] The dropdown still shows **your** model, not the box default.
- [ ] In devtools → Application → Cookies, `llmModel` still holds your model.

### 2.2 The agent-dispatched paths — the customer's actual bug

In **beginner** mode, on a non-default model, ask for something big enough that Leo offers
to switch to Plan mode, and accept the card:

- [ ] The dropdown still shows your model after the new thread is minted.

In **ticket** mode, on a non-default model, get a ticket card and click
**"implement this ticket"**:

- [ ] The dropdown still shows your model, and Leo's reply is from that model — no
      silent handover to the default mid-conversation.

### 2.3 A user who never chose still follows the box default

Clear the `llmModel` cookie, reload, and click **New thread**:

- [ ] The dropdown shows the box default.
- [ ] **`llmModel` is still not set.** This is the half that matters most: writing it here
      would pin the user to today's default forever, and a later fleet default change would
      never reach them again. Check the cookie explicitly — the dropdown looks identical
      either way.

### 2.4 The other two programmatic switches must not persist either

- [ ] Attach an image while on a text-only model. Leo switches to the vision model and
      says so — afterwards `llmModel` is **unchanged** (you did not choose the vision
      model; you attached an image).
- [ ] On a box with `model_switching_allowed = false`, the picker is hidden and the default
      is pinned — `llmModel` is **unchanged**.

### 2.5 Nothing regressed from 0.7.7

- [ ] Pick a model, reload the page. It is still selected. (0.7.7's fix — the
      `remembered_model_survives_page_load` half.)

## 1. A stranger hitting a bad URL gets a plain 404

The bug: Leo boxes run `RAILS_ENV=development` on purpose, so
`consider_all_requests_local` was true for **everyone**. Any unrouted request returned
the ~100 KB Rails developer error page to an anonymous visitor — including the customer
app's entire route table (368 routes on `qa-candidate`, `/admin/users/:id/impersonate`
among them), the engine's file layout and the request env dump. No session, no token, no
header needed, while WordPress scanners were walking the fleet.

**The trap this plan exists to avoid:** the specs run in `RAILS_ENV=test` while the site
runs in `development`. A green suite proves nothing here. Every check below must be run
with `curl` against the **public** URL — not a browser tab you are already signed into,
and not the test suite. This is the same trap as SI#418.

### 1.1 Anonymous — the check that matters

From a machine that has never signed into the box (or just use `curl`, which carries no
cookies):

```
curl -s -o /tmp/404.html -w "%{http_code} %{size_download}\n" \
  https://rails-<box>.leo.llamapress.ai/no-such-path-xyz
grep -c 'impersonate\|route_table' /tmp/404.html
```

- [ ] Status is **404** and the size is **~1.7 KB**, not ~100 KB.
- [ ] The grep prints **0**.
- [ ] Opening `/tmp/404.html` shows the plain "The page you were looking for doesn't
      exist (404)" page — no route list, no source extract, no env dump.

Measured on `llamapress-dev` before/after: **100,025 bytes → 1,722 bytes**, leak markers
32 → 0.

### 1.2 Signed in — you must NOT have lost the debug page

Sign in to the box's Rails app as a normal user, then, in that same browser:

- [ ] Visit `/no-such-path-xyz`. You still get the **full developer error page with the
      route table**. (Measured: 100,214 bytes, 32 markers.)
- [ ] Trigger a real application error (e.g. ask Leo to write a controller action that
      raises). You still get the full debug page with the backtrace and source extract.

If either of these shows the plain page, the guard is too aggressive — that is a
regression, not a fix.

### 1.3 Leo's debug loop still works

Leo reads crashes from the errors feed, not from the HTML page, so this should be
unaffected. Confirm it anyway:

- [ ] Ask Leo to write code that crashes a page, then ask it to fix it. It should notice
      the crash mid-turn and repair it, exactly as in 0.7.4.
- [ ] `curl -s -o /dev/null -w "%{http_code}\n" https://rails-<box>.leo.llamapress.ai/llama_bot/errors`
      returns **403** (alive and agent-gated), not 404 or 500.

### 1.4 Sanity — development mode is still on

- [ ] Editing a view on the box still takes effect without a restart. (If this broke,
      something other than the exception flag got changed.)

## Notes for the reviewer

- **Placement.** The guard is inserted **after** `ActionDispatch::DebugExceptions`, which
  in a Rack stack means *inside* it. The ticket suggested "before"; before puts it
  outside, where DebugExceptions has already rendered the page by the time the exception
  arrives. `bundle exec rails middleware` should show `DebugExceptions` above
  `LlamaBotRails::DetailedExceptionsGuard`.
- **No IP or header trust.** An earlier draft also allowed loopback/private-IP requests
  to see details, so the agent kept the HTML page. That was dropped: it would have rested
  on Caddy always setting `X-Forwarded-For`, and the agent does not need the HTML page.
  Trust is a signed-in session and nothing else — there is no header an attacker can send
  to get the detailed page back.
- **It only ever narrows.** An app already running with `consider_all_requests_local =
  false` keeps that; being signed in never turns details back on.
- **Still open, not in this change:** `rack-attack (6.8.0)` is bundled on every box with
  no initializer. The ticket suggests shipping one (throttle by IP; hard-block `wp-json`,
  `wp-admin`, `wp-login.php`, `.env`, `.git/config`). That is a separate ticket.

## Goals (what we're actually changing)

1. **Soften Engineer Mode's *voice*, keep its engineering *muscle*.** Engineer Mode
   (`rails_agent`) should talk at a 7th-grade reading level and assume the user knows
   nothing about software beyond a few primitives. Every deep engineering capability
   (Turbo/Stimulus patterns, scaffolding, sub-agent orchestration, debugging discipline,
   data-modeling rules) stays exactly as-is — only the user-facing *talking* changes.

2. **A real Engineer Plan Mode.** When a user in Engineer Mode flips the **Plan**
   execution toggle, route them to a new planning agent that asks simple, one-at-a-time
   questions (the Beginner Plan Mode mechanism) but retains Engineer Mode's depth — instead
   of the current behavior, which sends *everyone* to the beginner-flavored plan agent.

## Recommendation on structure (you asked what I'd do)

**Option A — a new separate agent, reusing the existing Plan-Mode machinery.** This is both
"use what's created" *and* "a pattern we've done before":

- **Pattern we've done before:** every mode is its own package under
  `app/agents/leonardo/<name>/` (prompts + nodes + middleware) registered in
  `app/langgraph.json`. We add one more the same way.
- **Use what's created:** the new `rails_engineer_plan_mode_agent` is a near-clone of
  `rails_plan_mode_agent` — same `nodes.py`, same tools, same middleware, same
  `ask_user_question` one-question-per-turn loop. **Only the prompt differs.**
- **DRY on the engineering knowledge:** rather than copy `RAILS_AGENT_PROMPT`'s ~1900 lines
  of patterns, the new prompt is *composed* — it imports the (now softened-voice) engineer
  knowledge and wraps it in the plan workflow:
  `ENGINEER_PLAN_PROMPT = PLANNING_PREAMBLE + RAILS_AGENT_PROMPT_BODY`. One source of truth
  for "how to build Rails well," reused by both Engineer and Engineer-Plan.

Rejected **Option B** (one plan agent that branches internally): the single prompt would
have to serve two very different audiences and would drag Engineer's huge knowledge base
into the Beginner plan path. Separate agents keep each flow independently tunable and leave
Beginner Plan Mode untouched.

## Item 1 — Engineer Mode 7th-grade voice

**File:** `app/agents/leonardo/rails_agent/prompts.py`

Insert a new **"## How You Talk (user-facing)"** section near the top (right after
`## Core Principles`), and add one line noting that the deep technical sections below are
*internal knowledge for you, not a script for the user*.

### The tiered vocabulary policy (this is the heart of the change)

This is deliberately **one tier softer than Beginner Mode but not as locked-down**:
Beginner *bans* the basics; Engineer *allows* them with a gloss and *scales up* to the user.

- **Default to 7th-grade reading level.** Short words, short sentences, no walls of text.
- **Assume the user is smart but not an engineer.** They may know a *handful* of basics and
  nothing past them: `browser`, `database table`, `HTML element / page`, `JavaScript
  (front-end code that runs in the browser)`, `Ruby (back-end code that runs on the
  server)`. **Assume zero knowledge of** Rails, Hotwire, Turbo, Stimulus, scaffold,
  migration, MVC, controller, callback, partial, gem, etc.
- **Even the basics are a stretch — don't reach for them unless they're the clearest way
  to say something.** Prefer "the place your app saves info" over "database table" when you
  can.
- **When you do use a tech word — even a basic one like "database table" or "browser" —
  add a tiny plain gloss in parentheses the first time it appears in a reply.** Friendly,
  short, slightly educational, never condescending:
  - "I'll add a database table (a spreadsheet-like place where your app keeps its info)…"
  - "This runs in the browser (the Chrome or Safari window people look at)…"
  - "I'll put this in the back-end code (the part that runs on the server, not on the
    screen)…"
- **Match the user's level — scale up, never down.** If the user uses a technical term,
  use it back at the same level with no gloss. Once they show they know the words, keep
  meeting them there for the rest of the conversation. Advanced users get a peer, not a
  tutorial.
- **Translate, don't dumb down.** The engineering stays sophisticated; only the explanation
  is simple.
- **Never expose internal process/tooling** ("I used the Edit tool", tool names,
  "scaffold", "migration", middleware). Same rule Beginner/Plan already enforce.

I'll model the section on `rails_beginner_agent/prompts.py:38-75` (reuse its swap table as a
starting point) but rewrite the rule from "BANNED — never use" to "use sparingly, gloss on
first use, scale to the user."

**Scope guard:** I will *not* touch the internal "for you, not the user" sections (Turbo
patterns, orchestrator mode, data modeling, etc.). Those stay verbatim — they govern *how
it builds*, not *how it talks*.
